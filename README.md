# Concordance wiki

The configuration repository that publishes the Concordance project wiki at `https://concordance-wiki.github.io/demo-wiki`. It holds nothing but configuration: which sources to read, the profile override, the theme, the stopwords and the pipeline. The content lives in [demo-glossary](https://github.com/concordance-wiki/demo-glossary), [demo-specs](https://github.com/concordance-wiki/demo-specs) and [demo-briefs](https://github.com/concordance-wiki/demo-briefs), the working sessions of the project with their transcripts and decks, and the tool builds its own wiki from them.

Copy this repository to start a wiki of your own: change the sources in `concordance.yaml`, the name, logo and colours in `theme.yaml` (and drop `footer.credit`, which this wiki keeps because the tool is documenting itself), and the pipeline does the rest.

## The loop

1. An author changes a note in the glossary, in the specifications or in the briefs. The pull request is linted where it is written (`.github/workflows/lint.yml` of each content repository): the SARIF log lands in the margin of the diff and an error finding fails the check.
2. Once merged, the lint runs again on `main` and, when green, sends a `content-updated` dispatch to this repository.
3. The wiki workflow (`.github/workflows/pages.yml`) builds the site of the four repositories, the three sources cloned at their `main` ref at depth 1, and publishes `dist/` on GitHub Pages. It also runs on every push here, every morning at 05:00 UTC, and on manual dispatch, so that a dispatch lost for want of a token is caught up within a day.
4. The repository of the tool verifies on every change that the wiki still covers it (`scripts/parity.mjs`): every check has a rule note, every page slot a screen note, every active type a note, every top-level configuration key and every check family a glossary term.

Until the first release of the tool, every workflow builds the command line from a checkout of [the tool's repository](https://github.com/concordance-wiki/concordance) at `main`; once the `concordance` package is published, the build steps become the one-liners of the [pipelines guide](https://github.com/concordance-wiki/concordance/blob/main/docs/guides/pipelines.md).

Two steps are done by a person, once:

- GitHub Pages: in the settings of this repository, set Pages → Source to "GitHub Actions". Until then the workflow builds and the deploy job fails.
- The dispatch token: the automatic token of a run cannot reach another repository. Create a fine-grained personal access token with the "Contents: read and write" permission on this repository and store it as the `WIKI_DISPATCH_TOKEN` secret of each content repository. Without it the dispatch step is skipped and the nightly build takes over.

## Scenarios

The four repositories exercise every way a corpus can be described and every kind of file the tool reads, so that an integrator finds each mechanism at work rather than in a table. Each paragraph names the file that declares the mechanism and the notes that show it.

**Folders are free.** The glossary files its terms in thematic folders two levels deep (`ingestion/typing/type.md`, `inference/recognition/dictionary.md`) and the specifications nest their families (`rules/links/`, `screens/panels/`, `decisions/publication/`). The identifier of a note is its path, `glossary/inference/recognition/dictionary`, and every link between notes is a relative path the tool resolves file by file: the build reports no unresolved reference and no broken link after the move. One note keeps its former address through an `id:` in its frontmatter, `inference/recognition/keyword-page.md`, published as `glossary/keyword-page`: a link to it from outside the wiki still lands, which is what the identifier override is for, an address that must survive a move.

**Domains by folder** (`domains:` in `concordance.yaml`). Every domain is declared with `folder: true`: it claims the files that have a folder of its name on their path, in every source, so `ingestion/sources/source.md` of the glossary and `objects/ingestion/source.md` of the specifications are filed together. Two subdomains are folders under their parent's, `typing` under `ingestion/` and `recognition` under `inference/`; `objects/inference/recognition/keyword-page.md` lands in `inference/recognition` without a line of configuration. The families of the specifications whose folder is named after a type keep a glob on the domain that owns them, `screens/**` and `viewers/**` on `publication`, `rules/**` on `quality`, `api/**` on `inference`; and six notes say their domain in frontmatter because their folder says another: `domain: inference` on the relation typing and operation matching rules, `domain: publication` on the accessibility rule, `domain: quality` on the plugin API, `domain: inference/recognition` (the full path form) on the keyword page threshold decision, `domain: typing` (the short form) on `notes/type-by-filing.md`. The briefs have no domain folder: `ingestion`, the domain that owns transcripts and twin resources, claims `meetings/**` and `framing/**` by glob, which files the raw files that carry no frontmatter, and the minutes of a session say in frontmatter what the session was about, `domain: publication` on the theme override session. No note is unclassified.

**Typing by several routes** (`sources[].rules` in `concordance.yaml`; the model records the route on every entity, `type_origin` in `model.json`). A folder glob types most families (`screens/**`, `processes/**`, `objects/**`, `roles/**`, `batches/**`). A suffix types the rules, `match: { suffix: ".rule.md" }`, and is the only route for them: `rules/links/broken-link.rule.md` is `specs/rules/links/broken-link`, and the screens link to it by its file name with the suffix. A file name pattern types the two viewers filed outside `screens/`, `viewers/*-viewer.md`; the folder is part of the glob because `**/*-viewer.md` alone would also catch the decision about the contract viewer. The source's `default_type: decision` types what no rule names: the whole of `decisions/`, and `notes/type-by-filing.md`, a decision dropped in a folder the configuration never mentions. Two rules match the operations, `api/**` then `api/operations/**`, and the last one wins. The glossary is typed as a whole by the source's `type: term`. The briefs add the fourth route, an extension: `match: { ext: [".vtt"] }` types a transcript as a meeting wherever it is filed, beside the folder glob `meetings/**` that types every file of a session alike and the source's `default_type: document` that types the framing decks.

**Frontmatter wins.** The three tables under `data/` carry `type: data_object` and no rule names their folder. One note contradicts its folder on purpose: `screens/pages/exploring-the-site.md` is a process, the path a reader follows through the pages of the site, filed among the screens it walks through, and its frontmatter says `type: process`; the folder rule would have made it a screen, the frontmatter wins, and the model records `frontmatter` as the origin of its type. The frontmatter of a decision also carries `superseded_by`, see the profile below.

**Applications** (`applications:` in `concordance.yaml`). Three are declared: `concordance-cli`, the command line and its build, lint, render and export; `concordance-site`, the generated static site; `concordance-linter`, the lint as distributed to the forges. Both sources default to `concordance-cli` through their `application` key; the rule on `screens/**` and the one on `viewers/*-viewer.md` set `application: concordance-site` on the screens; `processes/quality/lint.md` moves to `concordance-linter` by its own frontmatter. Every entity has an application the configuration declares.

**Stopwords** (`inference.stopwords`). Three files combine on top of the language pack, each with a header saying what it holds: `stopwords.en.txt` for general English words, `stopwords.domain.txt` for the words of this corpus that name no concept, `stopwords.publication.txt` for the vocabulary of the user interface that the screen notes repeat, `button`, `region`, `keyboard`.

**Lock file** (`concordance.lock.yaml`). `rejected_terms` lists expressions the discovery proposed as `W-TERM-UNDEFINED` that are fragments cut across a comma or a full stop, and the sentence every rule note repeats. `duplicates.separated` lists four pairs the twin detection reported as `W-DUP-CANDIDATE` on the likeness of their base names alone: a term and a role both called reader, a term and an object both called entity, two terms whose spellings are close, two rules about the matching of operations. No pair is merged: every candidate of this corpus is two notes, and `merged` is for a deck and its notes or a transcript and its minutes. The build reads the file through the `lock` key, validates it against the published schema and applies both blocks: the eleven rejected expressions still proposed leave the findings, five of them their keyword page too, three of the separated pairs leave `W-DUP-CANDIDATE` and the fourth, the two configuration terms the reconciliation had merged on their base names alone, are two pages again; the summary counts the decisions applied. The `links` block of the schema is recorded, not read, and `validate-config` says so.

**Profile** (`profile.yaml`). Two additions to the default profile. The `decision` type gains a `superseded_by` attribute, a reference to a decision that produces the `supersedes` relation in the other direction (`inverse: true`). `decisions/publication/fonts-from-a-third-party-host.md` names the decision that replaced it, `decisions/publication/self-hosted-fonts.md` names the one it replaces with the default `supersedes`, and the build records one link with the two provenances. The `meeting` type gains a `source` attribute, the key the twin-resource reconciliation reads as a declaration and which the default profile declares for documents only, so that the minutes of a session may name their transcript without a `W-ATTRIBUTE-UNKNOWN` finding.

**Excluded files** (`privacy.exclude`). The README of each content repository describes the repository, not the tool; the configuration keeps them out of the corpus.

**Meetings** (`sources[].rules` on the `briefs` source; `meetings/2026/` in demo-briefs). A working session is a folder holding its minutes, a `.vtt` transcript and, for one of them, the deck shown. Every file of the folder is typed `meeting` by the folder glob; the page of the session stands on the minutes, with the transcript as a tab of timestamped cues, each cue naming its speaker and anchored so that a mention read in it cites its timecode, the duration derived from the last cue, and the callout "Decision taken here" pointing at the decision the session produced, which the minutes name by its identifier in the specifications under `decisions:`, a frontmatter reference that crosses sources without a line of configuration. The tree of the space groups the sessions by year and month because every note of the source carries a date.

**Documents and twins** (`convert: true` and `plugins:` in `concordance.yaml`; `framing/2026/` and the theme override session in demo-briefs). A deck is committed as its `.pptx` original and its `.pdf` preview next to its notes; the office reader gives the build its title and slide count, the LibreOffice converter its PDF and the text of every slide, cached by fingerprint under `.concordance-cache`, which the workflow keeps between runs. The reconciliation adds up the signals every pair of files shares, the same base name in the same folder, the title of the deck equal to the heading of the notes, the text of the preview repeating the text of the deck, the transcript declared by the minutes under `source:` (an attribute the profile adds to the meeting type, see below), and, once the repository is read from git, the commit that brought them, and merges the files above 0.9 into one entity: the framing deck is one document page with the tabs "Document", "Extracted text" and the downloads of both files, the theme override session one meeting page with four files, "same folder, same base name, title equal to the heading, declared in the frontmatter" under its properties. The pairs that only share a base name across folders stay separate with a `W-DUP-CANDIDATE` finding.

**Pseudonymisation** (`privacy` in `concordance.yaml`, `pseudonyms.yaml`). The transcripts name the four fictional participants of the corpus; the dictionary maps each name to a stable pseudonym and a role, `publish_transcripts: true` says that transcripts are part of the site, and the page of a meeting says "Pseudonymised participants". The dictionary is committed because the names are invented; a real wiki keeps it out of every public repository, as the [publishing transcripts](https://github.com/concordance-wiki/concordance/blob/main/docs/guides/publishing-transcripts.md) guide says. The build of this version validates the keys and labels the page, but does not yet replace the names in the cues, the fragment and the copied transcript: the pipeline never calls the pseudonymisation the core package ships. The [CHANGELOG](CHANGELOG.md) records it as the first finding of this loop.

**Contracts** (`plugins:` in `concordance.yaml`; `api/contracts/` in demo-specs). The model query API declares its OpenAPI contract by a relative path; the contract importer reads it, produces one operation per operation of the contract, matches each one to the operation note that names its operation id, so that the three notes absorb them, and the page of the API carries the operations table and the contract card, version, import date, download and the contract viewer island. A second API note declared a JSON schema as its contract at a URL that did not exist; the importer reported it unreachable and the note no longer declares one.

**Figures** (`screens/assets/` in demo-specs). The entity page embeds the sketch it was drawn from, an SVG on a line of its own; the build copies the file next to the page and shows it as a figure with its alternative text as the caption and the path of the file in its repository.

**Plugins** (`plugins:` in `concordance.yaml`). The configuration lists the four plugins the corpus needs, the VTT reader, the office reader, the LibreOffice converter and the OpenAPI importer, by package name, as a wiki built with the published preset would; the workflow exposes them from the checkout of the tool until the preset is published, and installs LibreOffice, without which the converter disables itself with a finding and the decks stay downloadable without preview.

## Building locally

```bash
node <tool>/packages/cli/dist/bin.js build --config concordance.yaml --output dist
```

reads the sources from GitHub. To build from local checkouts, copy `concordance.yaml`, replace each `git`/`ref` pair with `path: ../demo-glossary`, `path: ../demo-specs` and `path: ../demo-briefs`, and make the paths of the profile, the theme, the stopwords, the dictionary and the lock absolute if the copy is not in this folder; the copy stays out of this repository. The plugins must be resolvable from the core package of the checkout, as the workflow arranges, and LibreOffice installed for the decks; a local source has no commit, so the reconciliation of the briefs relies on the base names, the titles, the texts and the declared transcript alone, which is enough to group every session.

## First loop

The first build of this wiki from the tool's own checkout read 102 files and reported 950 findings, none an error: 556 recurring expressions without a note (`W-TERM-UNDEFINED`), 12 unresolved references (`W-REF-UNRESOLVED`: every screen named its roles, `reader`, `integrator`, `writer`, and no role note existed), 22 notes outside every domain (`W-DOMAIN-UNCLASSIFIED`), 10 homonyms (`I-TERM-HOMONYM`, two of them accidental: the alias `relation` shared by the terms "Link" and "Relation", the alias `LOCAL_CHECKS` shared by a glossary term and a rule) and 342 links left on the generic relation (`I-REL-AMBIGUOUS`). What changed, in the three repositories: seven role notes, and every screen now names its roles by path; the domain globs rewritten so that every note of the two repositories is filed, with a `recognition` subdomain; the two accidental aliases dropped; sixty-six glossary terms written for the expressions the tool found without a note (`type`, `pipeline`, `step`, `frontmatter`, `section`, `keyword`, `locale`, `attribute` among them) and for the public concepts that had no note, forty-one verbs and counters added to `stopwords.domain.txt` so that the discovery stops proposing them, and the missing specifications: twelve rules, one screen, three processes, ten decisions, one API, five objects, one batch, three tables and three operations. The [CHANGELOG](CHANGELOG.md) keeps the counts before and after.
