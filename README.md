# Concordance wiki

The configuration repository that publishes the Concordance project wiki at `https://concordance-wiki.github.io/demo-wiki`. It holds nothing but configuration: which sources to read, the profile override, the theme, the stopwords and the pipeline. The content lives in [demo-glossary](https://github.com/concordance-wiki/demo-glossary) and [demo-specs](https://github.com/concordance-wiki/demo-specs), and the tool builds its own wiki from them.

Copy this repository to start a wiki of your own: change the sources in `concordance.yaml`, the name, logo and colours in `theme.yaml` (and drop `footer.credit`, which this wiki keeps because the tool is documenting itself), and the pipeline does the rest.

## The loop

1. An author changes a note in the glossary or in the specifications. The pull request is linted where it is written (`.github/workflows/lint.yml` of each content repository): the SARIF log lands in the margin of the diff and an error finding fails the check.
2. Once merged, the lint runs again on `main` and, when green, sends a `content-updated` dispatch to this repository.
3. The wiki workflow (`.github/workflows/pages.yml`) builds the site of the three repositories, the two sources cloned at their `main` ref at depth 1, and publishes `dist/` on GitHub Pages. It also runs on every push here, every morning at 05:00 UTC, and on manual dispatch, so that a dispatch lost for want of a token is caught up within a day.
4. The repository of the tool verifies on every change that the wiki still covers it (`scripts/parity.mjs`): every check has a rule note, every page slot a screen note, every active type a note, every top-level configuration key and every check family a glossary term.

Until the first release of the tool, every workflow builds the command line from a checkout of [the tool's repository](https://github.com/concordance-wiki/concordance) at `main`; once the `concordance` package is published, the build steps become the one-liners of the [pipelines guide](https://github.com/concordance-wiki/concordance/blob/main/docs/guides/pipelines.md).

Two steps are done by a person, once:

- GitHub Pages: in the settings of this repository, set Pages → Source to "GitHub Actions". Until then the workflow builds and the deploy job fails.
- The dispatch token: the automatic token of a run cannot reach another repository. Create a fine-grained personal access token with the "Contents: read and write" permission on this repository and store it as the `WIKI_DISPATCH_TOKEN` secret of each content repository. Without it the dispatch step is skipped and the nightly build takes over.

## Scenarios

The three repositories exercise every way a corpus can be described, so that an integrator finds each mechanism at work rather than in a table. Each paragraph names the file that declares the mechanism and the notes that show it.

**Folders are free.** The glossary files its terms in thematic folders two levels deep (`ingestion/typing/type.md`, `inference/recognition/dictionary.md`) and the specifications nest their families (`rules/links/`, `screens/panels/`, `decisions/publication/`). The identifier of a note is its path, `glossary/inference/recognition/dictionary`, and every link between notes is a relative path the tool resolves file by file: the build reports no unresolved reference and no broken link after the move. One note keeps its former address through an `id:` in its frontmatter, `inference/recognition/keyword-page.md`, published as `glossary/keyword-page`: a link to it from outside the wiki still lands, which is what the identifier override is for, an address that must survive a move.

**Domains by folder** (`domains:` in `concordance.yaml`). Every domain is declared with `folder: true`: it claims the files that have a folder of its name on their path, in both sources, so `ingestion/sources/source.md` of the glossary and `objects/ingestion/source.md` of the specifications are filed together. Two subdomains are folders under their parent's, `typing` under `ingestion/` and `recognition` under `inference/`; `objects/inference/recognition/keyword-page.md` lands in `inference/recognition` without a line of configuration. The families of the specifications whose folder is named after a type keep a glob on the domain that owns them, `screens/**` and `viewers/**` on `publication`, `rules/**` on `quality`, `api/**` on `inference`; and six notes say their domain in frontmatter because their folder says another: `domain: inference` on the relation typing and operation matching rules, `domain: publication` on the accessibility rule, `domain: quality` on the plugin API, `domain: inference/recognition` (the full path form) on the keyword page threshold decision, `domain: typing` (the short form) on `notes/type-by-filing.md`. No note is unclassified.

**Typing by several routes** (`sources[].rules` in `concordance.yaml`; the model records the route on every entity, `type_origin` in `model.json`). A folder glob types most families (`screens/**`, `processes/**`, `objects/**`, `roles/**`, `batches/**`). A suffix types the rules, `match: { suffix: ".rule.md" }`, and is the only route for them: `rules/links/broken-link.rule.md` is `specs/rules/links/broken-link`, and the screens link to it by its file name with the suffix. A file name pattern types the two viewers filed outside `screens/`, `viewers/*-viewer.md`; the folder is part of the glob because `**/*-viewer.md` alone would also catch the decision about the contract viewer. The source's `default_type: decision` types what no rule names: the whole of `decisions/`, and `notes/type-by-filing.md`, a decision dropped in a folder the configuration never mentions. Two rules match the operations, `api/**` then `api/operations/**`, and the last one wins. The glossary is typed as a whole by the source's `type: term`.

**Frontmatter wins.** The three tables under `data/` carry `type: data_object` and no rule names their folder. One note contradicts its folder on purpose: `screens/pages/exploring-the-site.md` is a process, the path a reader follows through the pages of the site, filed among the screens it walks through, and its frontmatter says `type: process`; the folder rule would have made it a screen, the frontmatter wins, and the model records `frontmatter` as the origin of its type. The frontmatter of a decision also carries `superseded_by`, see the profile below.

**Applications** (`applications:` in `concordance.yaml`). Three are declared: `concordance-cli`, the command line and its build, lint, render and export; `concordance-site`, the generated static site; `concordance-linter`, the lint as distributed to the forges. Both sources default to `concordance-cli` through their `application` key; the rule on `screens/**` and the one on `viewers/*-viewer.md` set `application: concordance-site` on the screens; `processes/quality/lint.md` moves to `concordance-linter` by its own frontmatter. Every entity has an application the configuration declares.

**Stopwords** (`inference.stopwords`). Three files combine on top of the language pack, each with a header saying what it holds: `stopwords.en.txt` for general English words, `stopwords.domain.txt` for the words of this corpus that name no concept, `stopwords.publication.txt` for the vocabulary of the user interface that the screen notes repeat, `button`, `region`, `keyboard`.

**Lock file** (`concordance.lock.yaml`). `rejected_terms` lists expressions the discovery proposed as `W-TERM-UNDEFINED` that are fragments cut across a comma or a full stop, and the sentence every rule note repeats. `duplicates.separated` lists four pairs the twin detection reported as `W-DUP-CANDIDATE` on the likeness of their base names alone: a term and a role both called reader, a term and an object both called entity, two terms whose spellings are close, two rules about the matching of operations. No pair is merged: every candidate of this corpus is two notes, and `merged` is for a deck and its notes or a transcript and its minutes. The file follows the published schema; the build of this version accepts the `lock` key without reading the file and `validate-config` says so, so the findings the entries answer still appear in the counts below.

**Profile** (`profile.yaml`). One addition to the default profile: the `decision` type gains a `superseded_by` attribute, a reference to a decision that produces the `supersedes` relation in the other direction (`inverse: true`). `decisions/publication/fonts-from-a-third-party-host.md` names the decision that replaced it, `decisions/publication/self-hosted-fonts.md` names the one it replaces with the default `supersedes`, and the build records one link with the two provenances.

**Excluded files** (`privacy.exclude`). The README of each content repository describes the repository, not the tool; the configuration keeps them out of the corpus.

## Building locally

```bash
node <tool>/packages/cli/dist/bin.js build --config concordance.yaml --output dist
```

reads the sources from GitHub. To build from local checkouts, copy `concordance.yaml`, replace each `git`/`ref` pair with `path: ../demo-glossary` and `path: ../demo-specs`, and make the paths of the profile, the theme, the stopwords and the lock absolute if the copy is not in this folder; the copy stays out of this repository.

## First loop

The first build of this wiki from the tool's own checkout read 102 files and reported 950 findings, none an error: 556 recurring expressions without a note (`W-TERM-UNDEFINED`), 12 unresolved references (`W-REF-UNRESOLVED`: every screen named its roles, `reader`, `integrator`, `writer`, and no role note existed), 22 notes outside every domain (`W-DOMAIN-UNCLASSIFIED`), 10 homonyms (`I-TERM-HOMONYM`, two of them accidental: the alias `relation` shared by the terms "Link" and "Relation", the alias `LOCAL_CHECKS` shared by a glossary term and a rule) and 342 links left on the generic relation (`I-REL-AMBIGUOUS`). What changed, in the three repositories: seven role notes, and every screen now names its roles by path; the domain globs rewritten so that every note of the two repositories is filed, with a `recognition` subdomain; the two accidental aliases dropped; sixty-six glossary terms written for the expressions the tool found without a note (`type`, `pipeline`, `step`, `frontmatter`, `section`, `keyword`, `locale`, `attribute` among them) and for the public concepts that had no note, forty-one verbs and counters added to `stopwords.domain.txt` so that the discovery stops proposing them, and the missing specifications: twelve rules, one screen, three processes, ten decisions, one API, five objects, one batch, three tables and three operations. The [CHANGELOG](CHANGELOG.md) keeps the counts before and after.
